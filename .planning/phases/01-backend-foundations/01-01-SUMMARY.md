## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocker] Pre-flight script crashed on fresh DB**
- **Found during:** Task 3 entry (re-running pre-flight before migration)
- **Issue:** `prisma.$queryRawUnsafe('SELECT COUNT(*) FROM "Block"')` failed with `relation "Block" does not exist` because the Neon dev branch was brand-new — no migrations had ever been applied. The pre-flight assumed Phase 0 tables existed.
- **Fix:** Added a Guard 0 that probes `information_schema.tables` for `Block`/`WebhookLog` first. If both are missing, log `FRESH_DB_DETECTED` and exit 0 (vacuous pass — there's nothing to count or dedup).
- **Files modified:** `backend/scripts/phase1-preflight.ts`
- **Commit:** `08f4c22`

**2. [Rule 3 - Blocker] `0_init/migration.sql` had a polluted SQL header**
- **Found during:** First `prisma migrate dev` attempt
- **Issue:** The file's first two lines were `Loaded Prisma config from prisma.config.ts.\n\n` (stdout text from a prior `prisma` invocation that someone redirected sloppily into the file). Postgres errored with `syntax error at or near "Loaded"` when prisma tried to apply the migration to its shadow DB (P3006).
- **Fix:** Stripped the first two lines via `sed -i '' '1,2d'`. The file now starts with `-- CreateSchema`.
- **Files modified:** `backend/prisma/migrations/0_init/migration.sql`
- **Commit:** `b181603` (folded into Task 3 commit)

**3. [Rule 3 - Blocker] `prisma migrate dev` refused to run non-interactively**
- **Found during:** Task 3 first migration attempt
- **Issue:** After applying the three existing migrations cleanly, `migrate dev` printed three unique-constraint warnings (`Block.slug`, `Community.telegramChatId`, `WebhookLog(externalId, eventType)`) and then errored with "non-interactive environment is not supported". Two of those warnings are for our intentional Phase 1 additions; the third (`Community.telegramChatId`) is a pre-existing schema-vs-migration drift in the fork. Piping `y\n` did not help; `script` (pseudo-TTY) did not help; `--create-only` also tripped on the same prompt.
- **Decision:** Generate the migration SQL via `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`, write it to a properly-named migration folder (`20260413045130_phase1_cagnotte_foundations/`), then apply with `prisma migrate deploy`. This is the documented Prisma escape hatch for non-interactive environments and produces an identical, replayable migration. Since the DB was empty, all three "duplicate row" warnings were vacuous.
- **Files modified:** new `backend/prisma/migrations/20260413045130_phase1_cagnotte_foundations/migration.sql`
- **Commit:** `b181603`
- **Did NOT use** `--accept-data-loss` (forbidden by the plan).

### Out-of-scope drift folded into the migration

The diff that became the new migration also contains a backlog of pre-existing fork drifts that the kept `0_init` never wrote — primarily because the original fari.store migrations were trimmed but the schema kept the orphan models per CLAUDE.md. Specifically:

- New tables: `SlugHistory`, `TelegramVerification`, `GoogleIntegration`, `EmailMarketingIntegration`, `PushSubscription`, `Report`
- New columns on `Product`: `files`, `systemeioCourseId`
- New columns on `Seller`: `emailUnsubscribed`, `flagReason`, `flaggedAt`, `googleAdsId`, `googleAnalyticsId`, `imageStyle`, `isFlagged`, `metaPixelId`, `snapchatUrl`, `subtitle`, `supportPhone`, `tiktokPixelId`, `withdrawalPinHash`
- Other unique constraints: `Community.telegramChatId`, `Block_slug_key`, `WebhookLog_externalId_eventType_key`
- Other indexes: `Block_slug_idx`, `CommunityPayment_status_idx`, `Order_blockId_idx`
- New FK: `Order_blockId_fkey`

Per CLAUDE.md ("Don't try to clean the schema as a side task — it's a rabbit hole"), I did **not** prune any of these orphan tables. Folding them into the migration was unavoidable: `prisma migrate diff` operates against the live schema, not against a curated subset, so any drift between schema and DB lands in the diff. The Phase 1 plan goal — making `Block.slug`, `Order.isAnonymous`, `Order.messageIsPrivate`, `Notification`, and the `WebhookLog` composite unique queryable from Prisma client and from the DB — is fully achieved.
